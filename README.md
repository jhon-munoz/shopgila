# Shopgila

E-commerce application built for the Gila Software code challenge. It lets you manage a product catalog (CRUD), import products from a CSV, search them and purchase them with a simulated payment.

- **Backend:** Java 21, Spring Boot 4, Spring Data JPA, Flyway, PostgreSQL 17, MapStruct.
- **Frontend:** React 19, TypeScript, Vite, Tailwind CSS, TanStack Query, Zustand, React Router.
- **Packaging:** everything runs with Docker Compose (PostgreSQL, API and Nginx serving the web app).

## Run it

Requirements: Docker with Compose.

```bash
docker compose up --build
```

| Service | URL |
|---|---|
| Web app (shop) | http://localhost:3000 |
| Administration | http://localhost:3000/admin |
| API | http://localhost:8080 |
| Health check | http://localhost:8080/actuator/health |

If a port is busy, change it with `BACKEND_PORT` or `FRONTEND_PORT`, for example `BACKEND_PORT=8081 docker compose up --build`. Database credentials can be overridden with `POSTGRES_DB`, `POSTGRES_USER` and `POSTGRES_PASSWORD` (a `.env` file next to `compose.yaml` works). To start from scratch use `docker compose down -v`.

Load the example catalog from the administration screen (**Import CSV**) or with:

```bash
curl -F "file=@Code Challenge E-Commerce.csv" http://localhost:3000/api/v1/products/import
```

### Run it locally for development

```bash
cd backend && ./gradlew bootRun
cd frontend && npm install && npm run dev
```

`bootRun` starts PostgreSQL by itself from `backend/compose.yaml` (Spring Boot Docker Compose support). The Vite dev server proxies `/api` to `localhost:8080`, and the web app is served at http://localhost:5173.

### Tests

```bash
cd backend && ./gradlew test          # unit tests, no Docker needed
cd backend && ./gradlew build         # unit and integration tests, Docker required (Testcontainers)
cd frontend && npm test
```

## Features

- **Products:** create, read, update and delete. SKU is unique and stored in upper case.
- **CSV import:** columns `name, sku, description, category, price, stock, weight_kg`. Existing SKUs are updated, new ones are created and invalid rows are reported with their line number without stopping the import.
- **Search:** text (name, SKU, description), category, price range, in stock only, sorting and pagination. Filters live in the URL, so a search can be shared.
- **Purchase:** multi line cart, stock is discounted atomically and the payment is simulated.
- **UI:** shop, cart, order confirmation, product administration and CSV import with its report.

The example CSV was downloaded on **13 October 2026**.

## API

Base path `/api/v1`. Errors share one body: `statusCode`, `timestamp`, `message`, `description` and an optional `details` list (validation errors, one per field).

| Method | Path | Notes |
|---|---|---|
| GET | `/products` | `q`, `category`, `minPrice`, `maxPrice`, `inStockOnly`, `page`, `size`, `sort` |
| GET | `/products/categories` | Distinct categories |
| GET, PUT, DELETE | `/products/{id}` | 404 if it does not exist, 409 on duplicated SKU or if the product is part of an order |
| POST | `/products` | 201 with `Location` |
| POST | `/products/import` | Multipart field `file` |
| POST | `/orders` | 201, 400, 402 (payment declined), 404 or 409 (not enough stock) |
| GET | `/orders/{id}` | |

The payment is simulated: the token `tok_declined` is rejected, any other token is approved. The declined token is configurable with `shopgila.payment.decline-token`.

## Decisions and alternatives considered

**PostgreSQL instead of NoSQL.** The data is relational (products, orders and lines), stock must change atomically and search needs filters and sorting. A document store would make the transactional purchase harder for no gain. Schema changes are versioned with Flyway (`ddl-auto` is `validate`).

**Layered backend modeled after an existing service.** `controller`, `service`, `repository`, `model`, `dto`, `mapper`, `exception`, `helper` and `utils`. DTOs are kept apart from entities so the API contract does not depend on the tables, and MapStruct generates the mapping at compile time. A single `@RestControllerAdvice` turns every exception into the same error body and hides internal details of unexpected errors.

**UUID primary keys.** They are not guessable and are generated by the application. The alternative, sequential ids, is simpler but exposes the size of the catalog.

**CSV import: upsert by SKU with a partial result.** Re-importing the same file is idempotent. When a SKU is repeated inside the file the last row wins. Rows are validated with the same rules as the API; invalid ones are returned in a report (line, SKU, reason) instead of rejecting the whole file. The example file is intentionally dirty (repeated SKUs, blank rows, `$29.99`, `free` as price, negative stock, missing names) and the importer handles each case. Categories are free text because the file has around twenty of them.

**Purchases and stock.** The whole purchase is one transaction: the products are loaded with `SELECT ... FOR UPDATE` ordered by id (so concurrent purchases cannot deadlock), stock of every line is checked before anything is discounted, the payment is charged and the order is saved. If the payment is declined or anything fails, everything rolls back. The server computes prices and totals, and the order keeps a copy of SKU, name and unit price so later price changes do not alter history. An integration test runs ten concurrent buyers against five units and checks exactly five orders succeed. Optimistic locking (`@Version`) is also present as a second safety net. Pessimistic locking was chosen over optimistic retries because contention on the last units of a product is exactly the case where retries would pile up.

**Payment behind an interface.** `PaymentService` has a fake implementation. Replacing it with a real provider means writing one class.

**Frontend.** TypeScript mirrors the API contract. TanStack Query handles server state (caching, loading and error states), Zustand holds the cart (persisted in `localStorage`) and notifications, and Tailwind keeps the styling consistent without a component library. The cart is checked against fresh product data when it is opened, so changed prices and missing stock are shown before ordering. In production Nginx serves the app and proxies `/api` to the backend, so the browser talks to a single origin and no CORS configuration is needed.

## Limitations and next steps

- No authentication or roles: the administration screens are open, as the challenge does not ask for it.
- Orders with a declined payment are not stored; they only appear in the logs. Persisting them would need a separate transaction.
- Products that were purchased cannot be deleted. A soft delete would allow retiring them.
- Categories are read with a `SELECT DISTINCT`, fine for a catalog of this size; a dedicated table would be better if categories need their own data.
- There is no order history screen, only the confirmation of the order just placed.
